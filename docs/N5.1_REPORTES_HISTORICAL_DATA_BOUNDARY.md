## Decisión de persistencia histórica para N5.1.C

### A. Persistencia nueva genérica para el Centro de Reportes

**N/A por defecto.** N5.1.C no debe crear una tabla genérica `ReporteSnapshot`, un data warehouse, event sourcing ni una copia paralela de datos únicamente para alimentar el shell/centro de reportes.

Si una implementación posterior demuestra que un reporte material no puede satisfacer D1/D2/D3 mediante el contrato y la persistencia del dominio propietario, esa necesidad debe abrirse como gap explícito del dominio correspondiente y validarse antes de introducir una migración.

### B. Reportes administrativos y auditoría

Pueden consumir los contratos existentes de `IReporteAdministrativoService`. No se certifica aquí que toda auditoría sea append-only ni que editar un catálogo preserve automáticamente todos los campos históricos. D1/D2 permanecen pendientes de evidencia causal donde apliquen.

Los reportes que por contrato representen el **estado actual** de usuarios, accesos, roles o permisos no necesitan una snapshot histórica nueva solo por pertenecer al Centro de Reportes. Si se solicita una vista histórica de esos datos, se deberá demostrar primero la fuente histórica real disponible.

### C. Estados financieros

N5.1 debe reutilizar `IEstadoFinancieroService` y conservar el ownership del dominio financiero. No se afirma que períodos cerrados sean inmutables ni que el servicio ya conserve snapshots suficientes sin una prueba específica del dominio.

El Centro de Reportes no debe recalcular valores financieros históricos desde catálogos actuales. Si el contrato financiero no puede demostrar la semántica histórica requerida para un reporte solicitado, el caso queda `GAP` y debe resolverse en el dominio financiero, no mediante persistencia genérica inventada en N5.1.

### D. Inventario, ventas, costo y utilidad

El preflight identifica D3 como requisito futuro y permite `N/A` cuando N5.1 no ofrezca el reporte. Por tanto, N5.1.C **no presume** que líneas de venta, movimientos o productos ya almacenen todos los snapshots de costo/precio necesarios.

Antes de certificar un reporte histórico de costo/utilidad se debe inspeccionar la política de costeo y la persistencia reales y ejecutar la prueba D3. Si falta información histórica material, el gap pertenece al dominio transaccional dueño del dato y requiere decisión separada.

## Regla operativa para N5.1.D/E

Toda API o UI posterior que ofrezca filtros históricos debe:

1. pasar los filtros al contrato especializado dueño de los datos;
2. no reconstruir métricas históricas usando valores maestros actuales sin evidencia de que esa sea la semántica correcta;
3. fallar de forma explícita o mantener el escenario como `GAP/N/A` cuando no exista evidencia suficiente;
4. evitar introducir persistencia nueva por conveniencia de presentación.

La entrega Jules ATTEMPT2 fue `READY_FOR_VAEP`, con patch presente y correlación completa, pero se rechaza **causalmente** como integración literal por estas afirmaciones no suficientemente demostradas:
