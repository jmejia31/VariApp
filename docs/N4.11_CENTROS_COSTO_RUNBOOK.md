# N4.11 — Centros de costo — Runbook frontend

## Alcance

Runbook operativo y de diagnóstico para la interfaz Angular de Centros de costo en `Desarrollo`. No declara `LISTO_REAL`, no autoriza despliegues y no sustituye los gates VAEP.

## Comportamiento verificado

La pantalla carga centros de costo mediante `CentroCostoService.buscar` con `pagina=1`, `tamanoPagina=100` y el término de búsqueda actual. La UI distingue estados de carga, error y lista vacía; el error de carga muestra `No se pudieron cargar los centros de costo.` y ofrece `Reintentar`.

Las acciones de creación, edición, cambio de estado y eliminación están condicionadas por permisos runtime del módulo `Finanzas`: `Crear`, `Editar`, `Activar`, `Desactivar` y `EliminarLogico`.

El formulario exige `codigo` y `nombre`. Para `TipoCentroCosto.Sucursal`, `sucursalId` es obligatoria. Para los demás tipos, `sucursalId` debe quedar vacía. Durante guardado se bloquea el submit con `saving()` y, si la operación termina correctamente, se cierra el formulario, se muestra `Centro de costo guardado.` y se recarga el listado.

## Diagnóstico rápido

1. Si la pantalla queda en carga o muestra error, usar `Reintentar` y verificar que la petición de búsqueda llegue al servicio sin fallo HTTP.
2. Si el listado aparece vacío, confirmar el término de búsqueda activo antes de tratarlo como pérdida de datos; la UI usa el mismo estado vacío para cero resultados filtrados.
3. Si `Nuevo centro` o acciones por fila no aparecen, validar los permisos runtime de `Finanzas` antes de diagnosticar un fallo del componente.
4. Si el formulario no guarda una Sucursal, verificar que exista `sucursalId > 0`. Si el tipo no es Sucursal, eliminar cualquier `sucursalId` residual.
5. Si guardar falla, conservar el formulario abierto y revisar la respuesta causal del servicio; la UI muestra `No se pudo guardar el centro de costo.` y no debe asumirse persistencia.
6. Si activar/desactivar o eliminar falla, no inferir cambio de estado local: ambas operaciones dependen de la respuesta del servicio y el listado se recarga solamente después de éxito.

## Verificación después de corrección

Ejecutar los tests causales del componente, servicio y rutas de Centros de costo, además de lint/build frontend aplicables al `FUNCTIONAL_HEAD`. Confirmar manualmente que:

- búsqueda y `Reintentar` funcionan;
- estados loading/error/empty se renderizan de forma excluyente;
- permisos ocultan o muestran acciones correctamente;
- validación Sucursal/no-Sucursal falla de forma cerrada;
- create/update cierran formulario y recargan solo tras éxito;
- activate/deactivate/delete recargan solo tras éxito.

## Rollback seguro

Si una corrección frontend introduce una regresión, revertir únicamente el changeset causal en `Desarrollo` mediante un commit normal y volver a ejecutar los gates causales. No usar `reset`, force-push, ramas nuevas, merge a `main`, deploy ni cambios de Producción. La documentación no constituye por sí sola evidencia de rollback exitoso.

## Límites

Este runbook describe comportamiento observable del frontend vigente. No afirma disponibilidad de Producción, aislamiento multi-tenant, integridad de datos externos ni éxito de CI futuro. Cualquier discrepancia entre este documento y el código vivo debe resolverse a favor del código y de `docs/VAEP_AUTHORITY.md`.
