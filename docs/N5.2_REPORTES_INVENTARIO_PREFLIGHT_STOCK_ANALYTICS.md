# N5.2.A.3 — Preflight de Stock Analytics

## Alcance
Análisis de capacidades existentes y faltantes para reportes de rotación, bajo stock (low/out-of-stock), inventario sin movimiento (no-movement) y antigüedad (aging). Este es un documento preflight (documentation-only); no introduce implementaciones, migraciones ni código en producción.

## 1. Campos, umbrales y dimensiones

**Dimensiones existentes (Sucursal / Almacén / Ubicación):**
- La entidad `ExistenciaVariante` y `MovimientoInventario` no incluyen `SucursalId` explícitamente, ya que se deriva de `AlmacenId`.
- Dimensiones físicas directas: `AlmacenId` y opcionalmente `UbicacionAlmacenId` en la entidad `ExistenciaVariante`.

**Umbrales de stock:**
- La entidad `ExistenciaVariante` ya calcula dinámicamente propiedades computadas: `TieneStockBajo => StockDisponible <= StockMinimo` y `EstaAgotada => StockDisponible <= 0`.
- `Producto` y `ProductoVariante` conservan el umbral parametrizable `UmbralStockBajo` como superficie de compatibilidad/agregado; para reporting físico N5.2 la autoridad de cantidad debe reconciliarse contra `ExistenciaVariante` y no inferirse únicamente desde `ProductoVariante.Cantidad`.

## 2. Consultas y endpoints reutilizables

**Bajo stock / Out-of-stock:**
- `ExistenciaVarianteRepository.BuscarAsync(...)` expone flags de filtrado directo como `stockBajo` y `agotada`. Este filtro evalúa `StockDisponible <= StockMinimo` y `StockDisponible <= 0` respectivamente.
- `ProductoRepository.GetStockBajoAsync()` es una superficie legacy/agregada: su predicado real es `!p.Variantes.Any(v => !v.Eliminado && v.Activo && v.Cantidad > v.UmbralStockBajo)`. Por tanto devuelve productos para los que **no existe** una variante activa/no eliminada por encima del umbral; no equivale a “al menos una variante con stock bajo” y no debe tratarse como autoridad física del reporte sin reconciliar con `ExistenciaVariante`.
- `AutomatizacionService` contiene lógica de alertas para variantes operativas (`M12-STOCK-BAJO`), reutilizable como referencia de reglas para el reporte analítico.

**Rotación, sin movimiento (No-movement) y Antigüedad (Aging):**
- No existen consultas pre-construidas dedicadas al cálculo analítico de rotación, "sin movimiento" o antigüedad de lotes en el inventario actual.
- `MovimientoInventarioRepository` provee filtrado por tipo, producto y ventana de fechas, lo que permite extraer eventos de movimientos, pero el cálculo de antigüedad o índice de rotación debe orquestarse/proyectarse en una superficie analítica dedicada.

## 3. Ventanas de tiempo (Time Windows)

- Los movimientos preservan una marca temporal `Fecha`.
- Las consultas por `Desde`/`Hasta` sirven como base para ventanas de análisis. Para aging se necesita definir la semántica autoritativa de fecha de entrada/último movimiento y evitar inferir lotes cuando no exista esa granularidad.

## 4. Brechas (Gaps) Identificadas

1. **Rotación y Aging:** faltan endpoints/proyecciones dedicados para inventario sin movimiento y rotación; las superficies actuales son principalmente transaccionales.
2. **Parámetros de ventana:** falta un contrato analítico unificado para ventanas configurables como 30/60/90 días.
3. **Sucursal vs Almacén:** los reportes agregados por sucursal deben resolver explícitamente la relación de sus almacenes y preservar el alcance autorizado.
4. **Semántica dual de stock bajo:** coexisten filtros físicos de `ExistenciaVariante` y una consulta legacy sobre `ProductoVariante.Cantidad`; N5.2.B debe fijar explícitamente cuál contrato es autoritativo para cada reporte y evitar que la consulta legacy cambie la semántica del stock físico.
