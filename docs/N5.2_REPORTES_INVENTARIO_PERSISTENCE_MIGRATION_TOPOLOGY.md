# N5.2.C.4 — Topología de Migración y Rollback de Persistencia para Reportes de Inventario

## Propósito

Definir la topología de migración, backfill y rollback para los reportes de inventario (reconciliación y movimientos) evaluando si los contratos de N5.2.B requieren alteraciones físicas en la base de datos (DDL) y delineando la estrategia de rollback.

## 1. Análisis de Contratos N5.2.B frente a Persistencia

- **N5.2.B.1 Envelope Transversal**: Se basa en filtros abstractos. No requiere almacenamiento adicional de metadatos en tablas existentes.
- **N5.2.B.2 Valorización/Kardex**: Estipula la reutilización de `MovimientoInventario`, `AsignacionCostoMovimientoInventario`, `ExistenciaVariante`. Prohíbe inventar otra autoridad de ledger, lo que significa que el Kardex puede proyectarse desde el esquema actual usando LINQ/SQL al vuelo o con vistas, sin necesidad de agregar columnas a `MovimientoInventario`.
- **N5.2.B.3 Reconciliación Operativa**: Utiliza `ConteoInventarioDetalle`, `TransferenciaInventarioDetalle` y `AjusteInventarioDetalle`. El contrato exige no fabricar cantidades fuera de estas fuentes, implicando que las reglas de proyección pueden operar sobre las columnas de snapshot existentes (`CantidadAnteriorSnapshot`, `CantidadNuevaSnapshot`, `DiferenciaSnapshot`, etc.).

**Conclusión:**
La implementación de N5.2.C (reportes de inventario) es **proyeccional (lectura pura)**. Los contratos aprobados en N5.2.B no requieren modificar esquemas (DDL) de las tablas productivas de inventario (conteos, transferencias, ajustes, movimientos).

## 2. Topología de Migración (DDL)

- **Decisión:** No se requieren nuevas migraciones Entity Framework (DDL) en `backend/src/Infrastructure/Migrations/` para soportar las estructuras analíticas de N5.2.C.
- Las vistas materializadas o índices adicionales podrían evaluarse por rendimiento en fases posteriores, pero no son obligatorios para cumplir los contratos funcionales.

## 3. Topología de Backfill (Reconciliación de Datos Históricos)

- **Decisión:** No habrá backfill masivo (DML) para completar datos legacy.
- **Justificación:** El contrato `N5.2.B.2` define explícitamente cómo manejar datos legacy faltantes (ej: `AlmacenId` nulo significa ubicación no disponible y no debe rellenarse artificialmente). El contrato prohíbe reescribir la historia para forzar correlaciones inexistentes.

## 4. Topología de Rollback

Dado que no hay cambios DDL ni DML:
- **Nivel de Base de Datos:** No se requiere un script de rollback (Down migration) porque no hay Up migration.
- **Nivel de Aplicación:** El rollback consistirá únicamente en retirar o revertir el código C# que implemente las consultas LINQ/Dapper (los repositorios de lectura o proyecciones) y los controladores API correspondientes que se construyan en las siguientes facetas de N5.2.C/D.

## Dictamen
La topología de migración es **nula por diseño** para satisfacer N5.2.C. Cualquier intento de agregar columnas persistentes como `DiferenciaAnalitica` o un `LedgerSecundario` viola los contratos de `N5.2.B`.
