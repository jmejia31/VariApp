# N5.2 — Preflight de Topología API/UI de Reportes de Inventario

## Propósito

Mapear la topología transversal necesaria para los reportes de inventario (reconciliación y movimientos). Se identifican los activos existentes y los puntos de extensión (seams) donde se integrarán los nuevos contratos analíticos, sin alterar la semántica de negocio J1/J2/J3 ni los límites de seguridad J6. No se redefine la lógica productiva ni se escriben archivos J5.

## 1. Topologías Backend Existentes

Se ha verificado la existencia y reutilización potencial de las siguientes capas para proveer información a los reportes:

- **Controladores Operativos:**
  - `ConteosInventarioController.cs`
  - `TransferenciasInventarioController.cs`
  - `AjustesInventarioController.cs`
  - `MovimientosInventarioController.cs`

- **Servicios de Aplicación:**
  - `ConteoInventarioService.cs`
  - `TransferenciaInventarioService.cs`
  - `AjusteInventarioService.N14.Core.cs`
  - `MovimientoInventarioService.cs`

- **Contratos (DTOs):**
  - `ConteoInventarioDto.cs`
  - `TransferenciaInventarioDto.cs`
  - `AjusteInventarioDto.cs`
  - `MovimientoInventarioDto.cs`

- **Entidades de Dominio:**
  - `ConteoInventario.cs`
  - `TransferenciaInventario.cs`
  - `AjusteInventario.cs`
  - `MovimientoInventario.cs`

## 2. Topologías Frontend Existentes

- **Centro de Reportes (Entry Point):**
  - El componente `CentroReportesComponent` (`frontend/src/app/features/centro-reportes/centro-reportes.component.ts`) es el punto de entrada unificado para los reportes administrativos y financieros, orquestado mediante la ruta `/centro-reportes` en `app.routes.ts`.

- **Vistas y Componentes Operativos:**
  - Existen vistas especializadas bajo `/inventario/*` como `MovimientosListComponent` en `frontend/src/app/features/inventario/movimientos-list.component.ts` para la ruta `/inventario/movimientos`.
  - Otros componentes listados, como `TransferenciasListComponent` (`transferencias-list.component.ts`), demuestran la interfaz actual que soporta la operatoria de inventario, mas no un panel analítico transversal.

## 3. Límites de Dependencia (Dependency Boundaries)

- **Lógica de Negocio (J1/J2/J3):** Toda semántica de cálculo de diferencias (e.g., entre stock esperado vs. contado) y lógicas de autorización de inventario operan exclusivamente en los servicios de dominio correspondientes y **no** deben reimplementarse ni modificarse para este preflight.
- **Seguridad (J6):** Los permisos de visualización (RBAC) seguirán siendo gestionados a nivel de `CentroReportesComponent` o vistas hijas delegando a `PermisosRuntimeService`. No se definen permisos nuevos en esta fase.
- **Integración UI/API (J4):** Este rol cartografía la comunicación entre el frontend (el Centro de Reportes) y las interfaces de los nuevos DTOs/Servicios sin inmiscuirse en la persistencia.

## 4. Puntos de Extensión (Extension Points)

Para dar cumplimiento a la falta de un "contrato analítico explícito" (conforme a N5.2 RECONCILIACION_OPERATIVA), los puntos de extensión definidos son:

1. **Nuevo DTO Analítico Transversal:** Creación de un contrato de lectura exclusivo (ej. `ReporteInventarioReconciliacionFiltroDto` / `ReporteInventarioReconciliacionDto`) que consolide los orígenes (Conteo, Transferencia, Ajuste) sin depender del agrupamiento interno de cada entidad operativa.
2. **Endpoint y Ruta API:** Exposición de un endpoint analítico (por ejemplo, en un futuro `ReportesInventarioController` o servicio de extensión de `MovimientosInventarioController`) que entregue información proyectada y paginada al frontend, evitando llamadas N+1 desde la UI y no duplicando los endpoints de `AjustesInventarioController`, `ConteosInventarioController` o `TransferenciasInventarioController`.
3. **Seam en Frontend:** Inserción de una nueva vista/pestaña bajo la jerarquía del `CentroReportesComponent` (o una sección análoga de Reportes Administrativos) que consuma este DTO analítico.
