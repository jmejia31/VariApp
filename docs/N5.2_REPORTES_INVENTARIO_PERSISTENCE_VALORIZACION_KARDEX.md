# N5.2.C.2 — Plan de persistencia para Valorización y Kardex

## Propósito

Cerrar mediante `REVIEW_FIRST / QA_TAKEOVER` la faceta de persistencia de Valorización y Kardex usando los contratos aceptados de N5.2.B y el esquema vivo de `Desarrollo`. Este scope decide únicamente qué persistencia, índices o migraciones están demostrados como necesarios; no implementa N5.2.D, no ejecuta DDL/DML y no toca Producción.

## 1. Autoridades persistidas que se reutilizan

- `MovimientoInventario` continúa siendo la autoridad durable de la secuencia de movimientos para Kardex. Conserva `ProductoId`, `ProductoVarianteId`, `Fecha`, `StockAnterior`, `StockNuevo`, `AlmacenId`, `UbicacionAlmacenId`, `CorrelationId`, referencias tipadas y `CostoUnitario` nullable para compatibilidad histórica.
- `AsignacionCostoMovimientoInventario` es la autoridad histórica preferente del costo de salida cuando existen asignaciones persistidas; no se revaloriza historia con `Producto.Costo` corriente.
- `ExistenciaVariante` conserva la autoridad de stock físico/vivo para valorización de existencia actual. No se crea un ledger analítico paralelo.

## 2. Cobertura de índices demostrada en el HEAD vivo

`MovimientoInventarioConfiguration` ya declara, entre otros:

- `IX_MovimientosInventario_ProductoId`;
- índice por `ProductoVarianteId`;
- `IX_MovInv_Producto_Variante_Fecha_N15` sobre `(ProductoId, ProductoVarianteId, Fecha)`;
- `IX_MovimientosInventario_Almacen_Ubicacion`;
- `IX_MovInv_Almacen_Ubicacion_Fecha_N15`;
- índices por origen junto con `Fecha` para Compra, Venta, Consumo, Ajuste, Transferencia y Recepción;
- `(ReferenciaTipo, ReferenciaId)`;
- `(Causa, Fecha)`;
- `IX_MovimientosInventario_CorrelationId_Fecha`.

Esta cobertura demuestra que ya existen índices relevantes para filtros de producto, variante, ubicación, origen, causa y correlación. **No demuestra por sí sola que todos los query shapes futuros sean óptimos**, por lo que este scope no declara rendimiento PASS ni inventa un índice `(Fecha, Id)` que la configuración viva no define.

## 3. Orden, paginación y query shape

El contrato de N5.2.B.2 exige orden determinista por `(Fecha, Id)`. La futura implementación debe expresar ese orden en la consulta y aplicar scope/RBAC antes de paginar. La existencia de `Id` como identidad estable permite el tie-breaker contractual, pero cualquier decisión de añadir un índice específico para un query shape de paginación debe quedar respaldada por evidencia de plan/perfil (`EXPLAIN` o equivalente) en un entorno descartable.

Por tanto:

- no se autoriza cargar el histórico completo ni resolver paginación en frontend;
- no se asume que `Skip/Take` sea siempre la estrategia óptima;
- keyset u otra estrategia sólo se adopta cuando el query shape real y su plan lo justifiquen;
- no se añade un índice únicamente por anticipación.

## 4. Decisión de migraciones

Con la evidencia disponible en N5.2.C **no existe un requisito funcional demostrado para una nueva tabla, columna, backfill o migración de esquema** para Valorización/Kardex. Los contratos aceptados se pueden proyectar desde autoridades ya persistidas.

Esto no equivale a afirmar que jamás hará falta un índice adicional. Si N5.2.D/G demuestra un gap de rendimiento real:

1. el índice deberá corresponder a un query shape medido;
2. se comprobará semantic dedupe contra índices existentes;
3. la migración tendrá `Up`/`Down` simétricos;
4. la prueba será sobre MySQL descartable, nunca Producción;
5. la decisión deberá preservar escritura y rollback de forma causal.

## 5. Compatibilidad y rollback

- Histórico con ubicación no demostrable conserva `AlmacenId`/`UbicacionAlmacenId` nullable; no se backfillea inventando identidad física.
- Histórico con asignaciones de costo usa esas asignaciones; el fallback legacy a `MovimientoInventario.CostoUnitario` permanece explícito y nullable cuando corresponda.
- Si la futura implementación es sólo de consulta/API, rollback = revertir el delta funcional sin mutar historia.
- Si una medición futura justificara un índice, rollback = `Down()` validado en entorno descartable.
