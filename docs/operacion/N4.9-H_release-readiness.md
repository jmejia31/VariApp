## Preconditions de cutover

El cutover solo puede declararse READY cuando todas las condiciones siguientes sean verdaderas sobre evidencia fresca:

1. `N4.9.G` está cerrado/certificado y no existe dependencia funcional pendiente heredada.
2. `N4.9.H` tiene REVIEW_FIRST completado para sus entregables A/B/C/D o sustitución válida por QA_TAKEOVER cuando ATTEMPT2 se agotó.
3. Todos los gates CI causales aplicables al `FUNCTIONAL_HEAD` están terminales y en PASS; fallos legacy/no relacionados no se usan como evidencia causal.
4. P0 abiertos = 0 y P1 abiertos = 0 para el scope del parent.
5. La semántica API queda verificada: aislamiento por cliente actual, validación del límite permitido, ordenamiento determinista y respuestas de validación/error consistentes.
6. El artefacto/runbook presente en este archivo coincide con el scope exclusivo de `N4.9.H` y no contiene cambios ejecutables de Producción.
7. Existe owner operativo identificable para la decisión GO/NO-GO y un owner técnico para investigar cualquier fallo causal.

Si cualquiera de estas condiciones no puede demostrarse, el estado es `NO-GO` y `N4.9.H` no puede marcarse `LISTO_REAL`.

## Gates de cutover

### Gate G1 — Integridad funcional

PASS cuando el `FUNCTIONAL_HEAD` contiene el comportamiento requerido y sus pruebas causales terminalizan correctamente. Para el gap de semántica API de H, la referencia material es `b8cb440fa1879fc76a7c57b315baf07532c6fc0f`.

### Gate G2 — Review y QA

PASS cuando cada facet material pendiente está aceptada por REVIEW_FIRST. Si un R2 ya fue consumido y la evidencia es insuficiente, la única ruta permitida es `QA_TAKEOVER`; no existe R3.

### Gate G3 — Seguridad de release

PASS cuando no existen P0/P1 abiertos del scope y ninguna validación causal indica riesgo de aislamiento de cliente, RBAC o comportamiento API.

### Gate G4 — Reversibilidad

PASS cuando el cambio puede revertirse al `FUNCTIONAL_HEAD` previamente certificado sin depender de secretos nuevos, cambios irreversibles de datos o acciones directas sobre Producción desde VAEP.

### Gate G5 — Trazabilidad

PASS cuando BITACORA/COLA registran `CURRENT_PARENT`, `FUNCTIONAL_HEAD`, resultado de review/QA, gates causales y decisión GO/NO-GO sin usar commits control-plane como sustituto de evidencia funcional.

## Árbol de decisión GO / NO-GO / rollback

1. **¿G1–G5 están PASS y P0/P1=0?**
   - Sí → `GO_READY`; el parent puede pasar a certificación final `LISTO_REAL` conforme a la autoridad VAEP.
   - No → continuar al punto 2.
2. **¿Existe un fallo funcional causal reproducible?**
   - Sí → `NO-GO`; aislar únicamente el gap demostrado. Si ATTEMPT2 está agotado, usar `QA_TAKEOVER` y no R3.
   - No → continuar al punto 3.
3. **¿El bloqueo es CI legacy/no relacionado o control-plane?**
   - Sí → documentarlo como no causal; no debe congelar el cierre funcional.
   - No/indeterminado → `NO-GO` fail-closed hasta identificar causalidad.
4. **¿Una corrección posterior degrada un gate previamente PASS?**
   - Sí → detener promoción y volver al último `FUNCTIONAL_HEAD` certificado como referencia de rollback. No ejecutar deploy/merge desde VAEP.

## Triggers de rollback / NO-GO

Cualquiera de los siguientes eventos invalida GO_READY:

- regresión causal en aislamiento por cliente;
- validación de `limit` fuera del contrato o resultados no deterministas;
- fallo causal de RBAC/autorización;
- P0 o P1 abierto dentro del scope;
- CI causal terminal en FAILURE;
- artifact de review con `semanticMatch=false`, `noOpRisk=true` o sin verificación suficiente después de ATTEMPT2;
- divergencia entre el comportamiento probado y el `FUNCTIONAL_HEAD` que se pretende certificar;
- necesidad de tocar secretos, Producción, `main`, merge o deploy para completar el parent.

## Procedimiento de reversibilidad

VAEP no ejecuta rollback productivo. La preparación reversible consiste en:

1. identificar y registrar el último `FUNCTIONAL_HEAD` certificado anterior al cambio causal;
2. aislar el changeset funcional que introdujo el fallo;
3. comprobar que no existen migraciones destructivas o dependencias irreversibles dentro del scope de H;
4. producir una corrección/reversión únicamente en `Desarrollo` bajo QA_TAKEOVER cuando corresponda;
5. volver a ejecutar únicamente los gates causales aplicables;
6. mantener `NO-GO` hasta recuperar PASS y P0/P1=0.

## Roles y escalamiento

- **VAEP controller:** decide REVIEW_FIRST/QA_TAKEOVER, causalidad de gates y certificación `LISTO_REAL`; no despliega.
- **Owner Jules de la facet:** produce el artifact/patch del scope exclusivo y evidencia de sesión útil.
- **QA takeover:** resuelve el gap material cuando ATTEMPT2 está agotado o la evidencia Jules no es verificable.
- **Owner de release/operación:** ejecuta fuera de VAEP cualquier decisión productiva autorizada por el proceso institucional.

Escalamiento: P0/P1 o pérdida de aislamiento de cliente ⇒ NO-GO inmediato y QA_TAKEOVER/owner técnico; CI legacy/no causal ⇒ registrar y continuar evaluación sin HEAD_FREEZE_CAUSAL funcional.
