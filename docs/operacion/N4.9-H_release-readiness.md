## Preconditions de cutover

`N4.9.H` sólo puede declararse `GO_READY` / `LISTO_REAL` cuando se demuestran todas las condiciones siguientes sobre evidencia fresca:

1. `N4.9.G` está cerrado/certificado y no existe dependencia funcional heredada pendiente.
2. A y B están aceptados por `REVIEW_FIRST` o sustitución válida según la autoridad.
3. C está resuelto por `REVIEW_FIRST`/`QA_TAKEOVER` sin R3 y el comportamiento material coincide con el `FUNCTIONAL_HEAD`.
4. D tiene release-readiness/rollback alineado al scope real; cualquier R2 insuficiente se resuelve por `QA_TAKEOVER`, nunca R3.
5. Todos los gates CI **causales y aplicables** al `FUNCTIONAL_HEAD` están terminales y sin failure causal; CI legacy, Vercel, deploy o control-plane no relacionado no congelan la certificación.
6. P0 abiertos = 0 y P1 abiertos = 0 para el scope del parent.
7. La semántica de períodos contables queda verificable: superposición = conflicto, recurso de cierre inexistente = no encontrado y transición de cierre inválida = conflicto.
8. El runbook no requiere secretos nuevos, cambios irreversibles de datos ni operaciones directas sobre Producción.

Si cualquiera de estas condiciones no puede demostrarse, el estado permanece `NO-GO` y `N4.9.H` no se marca `LISTO_REAL`.

## Gates de cutover

### Gate G1 — Integridad funcional

PASS cuando el `FUNCTIONAL_HEAD` contiene el comportamiento requerido y sus validaciones causales están terminales. Para el gap material identificado durante REVIEW_FIRST de C, la referencia funcional es `b8cb440fa1879fc76a7c57b315baf07532c6fc0f`.

### Gate G2 — Review y QA

PASS cuando las facets A/B/C/D pendientes han sido aceptadas por REVIEW_FIRST o resueltas por QA_TAKEOVER conforme a la política. Si ATTEMPT2 se agotó, no existe R3.

### Gate G3 — Semántica API de PeriodoContable

PASS cuando se preserva el contrato API esperado para las operaciones del scope:

- creación con rango superpuesto → conflicto (`409` mediante `ConflictException` en el pipeline HTTP vigente);
- cierre de ID inexistente → no encontrado (`404` mediante `ResourceNotFoundException`);
- cierre incompatible con el estado actual → conflicto (`409` mediante `ConflictException`);
- errores de validación de entrada permanecen separados de conflictos de estado/dominio.

### Gate G4 — Reversibilidad

PASS cuando el changeset funcional puede revertirse en `Desarrollo` al último `FUNCTIONAL_HEAD` certificado anterior sin migraciones destructivas, secretos nuevos ni acciones directas de Producción.

### Gate G5 — Trazabilidad

PASS cuando COLA/BITACORA registran `CURRENT_PARENT`, `FUNCTIONAL_HEAD`, review/QA, causalidad CI, decisión GO/NO-GO y referencias de rollback sin sustituir evidencia funcional por control-plane.

## Árbol GO / NO-GO / rollback

1. **¿G1–G5 están PASS y P0/P1=0?**
   - Sí → `GO_READY`; puede ejecutarse la certificación final `LISTO_REAL` conforme a la autoridad VAEP.
   - No → continuar al punto 2.
2. **¿Existe un fallo funcional causal reproducible?**
   - Sí → `NO-GO`; aislar únicamente el gap demostrado. Si ATTEMPT2 se agotó, usar QA_TAKEOVER y no R3.
   - No → continuar al punto 3.
3. **¿El bloqueo es legacy/no relacionado/control-plane?**
   - Sí → registrarlo como no causal y continuar evaluación sin `HEAD_FREEZE_CAUSAL` funcional.
   - No/indeterminado → `NO-GO` fail-closed hasta identificar causalidad.
4. **¿Una corrección posterior degrada un gate previamente PASS?**
   - Sí → detener promoción y usar el último `FUNCTIONAL_HEAD` certificado como referencia de rollback. VAEP no ejecuta deploy ni rollback productivo.

## Triggers de rollback / NO-GO

Cualquiera de los siguientes invalida `GO_READY`:

- permitir superposición de períodos cuando debe rechazarse;
- cierre de un ID inexistente sin semántica not-found;
- cierre repetido/inválido que no se represente como conflicto;
- mutación retroactiva no autorizada de un período cerrado;
- P0/P1 abierto dentro del scope;
- CI causal terminal en failure;
- artifact con `semanticMatch=false`, `noOpRisk=true` o evidencia insuficiente después de ATTEMPT2;
- divergencia entre comportamiento probado y `FUNCTIONAL_HEAD`;
- necesidad de tocar secrets, Producción, `main`, merge o deploy para completar el parent.

## Procedimiento de reversibilidad

VAEP no ejecuta rollback productivo. La preparación reversible consiste en:

1. registrar el último `FUNCTIONAL_HEAD` certificado anterior al changeset causal;
2. aislar el changeset funcional que introdujo el fallo;
3. confirmar que el scope no introduce migraciones destructivas/dependencias irreversibles;
4. producir una corrección o reversión únicamente en `Desarrollo`, usando QA_TAKEOVER cuando corresponda;
5. volver a ejecutar únicamente los gates causales aplicables;
6. mantener `NO-GO` hasta recuperar PASS y P0/P1=0.

## Roles y escalamiento

- **VAEP controller:** decide REVIEW_FIRST/QA_TAKEOVER, causalidad y certificación; no despliega.
- **Owner Jules de la facet:** produce patch/artifact de scope exclusivo y evidencia de sesión útil.
- **QA_TAKEOVER:** resuelve el gap material tras ATTEMPT2 agotado o evidencia Jules insuficiente; no crea R3.
- **Owner release/operación:** ejecuta fuera de VAEP cualquier decisión productiva autorizada.

Escalamiento: P0/P1 o regresión causal de períodos contables ⇒ `NO-GO` inmediato y owner técnico/QA_TAKEOVER; CI legacy/no causal ⇒ registrar y continuar sin freeze funcional.
