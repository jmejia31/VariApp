# N5.1 — Preflight de arquitectura del Centro de Reportes

## Propósito

Registrar las capacidades reutilizables y los límites arquitectónicos observables antes de implementar un centro de reportes independiente. Este preflight no crea servicios, controladores, permisos ni UI nueva.

## 1. Capacidades existentes reutilizables

### Reportes administrativos

- Backend: `backend/src/Infrastructure/Services/ReporteAdministrativoService.cs` implementa `IReporteAdministrativoService`.
- API: `backend/src/API/Controllers/ReportesAdministrativosController.cs`.
- Frontend: `frontend/src/app/features/reportes-administrativos/reportes-administrativos.component.ts` y `frontend/src/app/services/reporte-administrativo.service.ts`.
- Funciones observables: resumen administrativo, usuarios/accesos, roles/permisos, resumen de auditoría y exportación CSV/XLSX para los tipos soportados.
- Persistencia: el servicio consulta `AppDbContext` y usa consultas `AsNoTracking()` para lecturas.

### Estados financieros

- Backend: `backend/src/Infrastructure/Services/EstadoFinancieroService.cs` implementa `IEstadoFinancieroService`.
- Frontend HTTP: `frontend/src/app/services/estado-financiero.service.ts`, con endpoint base `/estados-financieros`.
- Consumidor UI observable: `frontend/src/app/features/estados-financieros/estados-financieros.component.ts`.

Estas capacidades existen como contratos especializados. N5.1 no debe duplicar su lógica únicamente para presentar una entrada de navegación unificada.

## 2. Decisión de reuse/boundary para el preflight

1. **Reusar contratos especializados existentes.** Un futuro centro puede componer capacidades ya expuestas por reportes administrativos y estados financieros sin copiar sus algoritmos.
2. **Mantener ownership de dominio.** La lógica financiera debe continuar perteneciendo al servicio financiero; la lógica de auditoría/RBAC administrativo debe continuar perteneciendo al servicio administrativo salvo requisito aprobado que justifique refactor.
3. **La unificación inicial puede ser de navegación/orquestación.** No se requiere crear un nuevo dominio persistente solo para ofrecer una pantalla central.
4. **No introducir todavía una interfaz/facade nueva.** Si N5.1.B demuestra necesidad de combinar datos de varios dominios en una sola consulta, entonces debe diseñarse el seam mínimo con pruebas; este preflight no inventa `IReporteCentralService` ni otro contrato inexistente.
5. **No inventar permisos.** El árbol actual ya usa `ReportesAdministrativos` y permisos del área financiera. Cualquier nuevo módulo/acción de autorización requiere decisión explícita y migración/grants coordinados; no forma parte de N5.1.A.

## 3. Seams futuros mínimos, solo si el alcance los exige

- Ruta/shell frontend independiente que pueda enlazar o componer vistas existentes.
- Contrato de autorización explícito y alineado frontend/backend.
- Adaptador/orquestador de aplicación únicamente cuando una vista necesite combinar resultados de servicios especializados en una operación coherente.
- DTO agregado únicamente cuando exista un caso de uso que no pueda expresarse con DTOs actuales sin acoplamiento indebido.
- Política de filtros, límites y exportación común solamente donde sea necesario para experiencia consistente; no reemplazar reglas de dominio existentes sin evidencia.

## 4. Fuera de alcance de N5.1.A

- Implementar el centro independiente.
- Cambiar lógica interna de `ReporteAdministrativoService` o `EstadoFinancieroService`.
- Crear migraciones o tablas nuevas.
- Crear un nuevo módulo RBAC o grants.
- Cambiar contratos productivos, secretos, deploy o Producción.
- Declarar que una facade, CQRS físico, cache, read replica o background jobs son obligatorios sin medición/requisito.

## 5. Criterio de aceptación arquitectónico

N5.1.B debe poder demostrar que cualquier seam nuevo resuelve una necesidad concreta sin duplicar lógica ya existente, conserva autorización fail-closed, mantiene los módulos transaccionales fuera del scope y dispone de pruebas de regresión sobre los contratos reutilizados.

Este documento es una decisión de límites para preflight; no declara integración funcional ni `LISTO_REAL` del parent.
