## 2. Topología contable observada en código

### `backend/src/Application/Services/AsientoContableApplicationService.cs`

`AsientoContableApplicationService` es una clase `static` y actualmente contiene dos responsabilidades puras:

- `CrearAggregate(CrearAsientoContableDto dto)`: normaliza concepto/campos opcionales, exige al menos dos detalles, crea el agregado, agrega cada `AsientoDetalle` y ejecuta `ValidarCuadre()`.
- `Mapear(AsientoContable entity)`: proyecta entidad y detalles a `AsientoContableDto` y calcula `TotalDebe` / `TotalHaber`.

No recibe `AppDbContext`, no abre transacciones, no hace `SaveChangesAsync` y no registra auditoría.

### `backend/src/API/Controllers/AsientosContablesController.cs`

La persistencia actual está controller-owned:

- GET lista `AppDbContext.AsientosContables`, incluye detalles y cuenta contable y pagina el resultado.
- GET por id consulta el agregado con detalles/cuentas.
- POST llama `AsientoContableApplicationService.CrearAggregate(dto)`.
- Si existe `Numero`, el POST busca un asiento previo por ese número y devuelve el existente como replay.
- Resuelve las cuentas contables referenciadas y rechaza cuenta inexistente, inactiva o que no acepta movimientos.
- Abre transacción explícita, agrega el asiento, ejecuta `SaveChangesAsync`, registra auditoría estricta y hace commit.

Consecuencia arquitectónica: **los procesos de venta/compra/cobro/pago/inventario no deben invocar el HTTP controller para contabilizar**. Antes del auto-posting se necesita una frontera application-level reutilizable que encapsule las invariantes de persistencia existentes.

### `backend/src/Domain/Entities/Contabilidad/AsientoContable.cs`

El agregado conserva `DocumentoOrigenId` y `TipoDocumentoOrigen`, además de `Numero`; mantiene detalles internos y `ValidarCuadre()` exige igualdad exacta entre total Debe y total Haber.

## 3. Gaps demostrados

1. **No existe hoy una frontera application-level reutilizable para persistir un asiento.** El helper de Application construye/mapea, mientras la persistencia y la auditoría viven en el controller.
2. **La idempotencia observable del endpoint POST está basada en `Numero`.** `DocumentoOrigenId` / `TipoDocumentoOrigen` existen en el agregado, pero este preflight no atribuye una restricción única de base de datos a esos campos sin evidencia de configuración/migración.
3. **No existe evidencia suficiente en el R2 para afirmar cobertura automática de venta, compra, cobro, pago, inventario, costo de venta, devolución, ajuste, caja y banco.** Cada seam debe mapearse por ruta/símbolo antes de conectarlo.
4. **No existe base para afirmar manejo de concurrencia optimista específico del motor contable** en el código inspeccionado; debe diseñarse/validarse explícitamente si el slice lo requiere.

## 4. Boundary de implementación seguro — siguiente slice

El siguiente slice permitido de N4.8.A debe ser pequeño y previo a conectar eventos de negocio:

### Slice A — extraer un writer application-level reutilizable

Objetivo: trasladar la lógica de persistencia del POST a una frontera de aplicación reutilizable sin cambiar el comportamiento observable del endpoint.

Debe encapsular como mínimo:

1. construcción/validación del agregado mediante la lógica existente;
2. replay/idempotencia actual por `Numero`;
3. validación de cuentas existentes/activas/que aceptan movimientos;
4. transacción;
5. persistencia;
6. auditoría estricta;
7. retorno del DTO mapeado.

El controller debe quedar como adaptador HTTP y delegar al writer. **Este slice todavía no debe conectar venta/compra/etc.** Esa integración debe entrar sólo después de que la frontera reutilizable tenga tests y CI verdes.

## 5. Slices posteriores dependency-valid

Cada seam debe declarar antes de implementar: evento disparador, identificador de origen, cuentas Debe/Haber, fuente de configuración, excepción por cliente, política de replay/idempotencia, transacción/rollback y pruebas.

## 6. Riesgos y controles

- **Doble contabilización:** no confiar sólo en retries de transporte. Definir llave estable de origen y constraint/guard apropiado antes del auto-posting.
- **Desbalance:** conservar `ValidarCuadre()` y probar ambos lados del asiento.
- **Cuenta inválida:** conservar las validaciones actuales de existencia/actividad/acepta movimientos.
- **Auditoría perdida al extraer:** el writer debe preservar el registro estricto actual.
- **Transacción parcial:** el refactor inicial debe mantener la semántica transaccional existente; la atomicidad entre documento de negocio y asiento se diseña en el seam concreto.
- **Drift funcional del endpoint:** pruebas de regresión deben demostrar que POST/GET mantienen contrato y replay actual.

## 7. Matriz mínima de pruebas del Slice A

1. creación de asiento balanceado con dos o más detalles;
2. rechazo de asiento desbalanceado;
3. rechazo de concepto vacío / detalles insuficientes;
4. rechazo de cuenta inexistente;
5. rechazo de cuenta inactiva;
6. rechazo de cuenta que no acepta movimientos;
7. replay por `Numero` sin segundo asiento;
8. persistencia + auditoría en la misma ruta de éxito;
9. regresión del contrato HTTP POST y GET;
10. prueba negativa que demuestre que el refactor todavía no dispara asientos desde un proceso de negocio.
