# N5.2.C.3 — Persistencia de Reconciliación de Inventario

## Decisión

**No se justifica una tabla, ledger paralelo ni migración estructural nueva para materializar la reconciliación analítica.** El contrato aceptado en N5.2.B.3 puede proyectarse desde las fuentes operativas existentes, sujeto a que N5.2.D implemente una consulta server-side paginada y N5.2.G demuestre su comportamiento/rendimiento.

## 1. Fuentes causales existentes

### Ajustes

`AjusteInventarioDetalle` ya materializa al confirmar:

- `CantidadAnteriorSnapshot`;
- `CantidadNuevaSnapshot`;
- `DiferenciaSnapshot`;
- `CostoUnitarioSnapshot`;
- `ImpactoCostoSnapshot`.

La proyección aceptada conserva `CantidadEsperada = CantidadAnteriorSnapshot`, `CantidadObservada = CantidadNuevaSnapshot` y `DiferenciaNormalizada = DiferenciaSnapshot`. Los campos económicos permanecen sujetos al RBAC/censura aceptado.

### Transferencias

`TransferenciaInventarioDetalle` conserva cantidades despachadas, recibidas, faltantes, sobrantes y dañadas. La proyección aceptada usa:

- `CantidadEsperada = CantidadDespachada`;
- `CantidadObservada = CantidadRecibida + CantidadDanada + CantidadSobrante`;
- `DiferenciaNormalizada = CantidadSobrante - CantidadFaltante`.

La fila sólo se considera terminalmente reconciliable cuando la evidencia de `RecepcionCerrada` satisface la invariante `CantidadRecibida + CantidadFaltante + CantidadDanada == CantidadDespachada`. No se reinterpreta daño como diferencia neta.

### Conteos

`ConteoInventarioDetalle` conserva `StockEsperadoSnapshot`, `CantidadContada` y la diferencia materializada por el ciclo. La proyección debe respetar el conteo ciego: stock esperado/diferencia no pueden revelarse mientras el ciclo operativo lo prohíba.

## 2. Estrategia de lectura

- Proyección de sólo lectura (`AsNoTracking()` cuando aplique EF Core).
- Scope físico/RBAC aplicado server-side antes de materializar resultados.
- Cada origen se normaliza al DTO analítico aceptado, preservando documento fuente y correlación cuando exista evidencia durable.
- **No se acepta paginar después de consolidar colecciones completas en memoria.** La implementación deberá resolver una consulta paginable de servidor —por ejemplo una composición traducible/UNION compatible o una estrategia equivalente que mantenga filtros, orden global determinista, `COUNT` y página en la base— y demostrarla con pruebas/plan de consulta antes de cerrar la fase funcional.
- Si EF no puede traducir una composición segura, N5.2.D deberá usar una alternativa explícita y testeable; no se permite degradar silenciosamente a N+1 o materialización completa.

## 3. Migración e índices

Este scope documental no demuestra necesidad de nueva migración. Cualquier índice adicional debe surgir de un query shape concreto y evidencia de plan/perfil; no de una lista genérica de índices supuestamente necesarios.

Si N5.2.D/G demuestra un gap real, el cambio deberá ser mínimo, no duplicar índices existentes, incluir `Up/Down` simétrico y validarse en MySQL descartable. Producción permanece fuera de alcance.

## 4. Rollback

- Mientras no haya cambio de esquema, el rollback es revertir la implementación de consulta/proyección sin alterar datos operativos.
- Si posteriormente se autoriza un índice, su `Down()` debe ser verificable en entorno descartable.
- No se autoriza backfill, restore, migración productiva ni segundo ledger.
