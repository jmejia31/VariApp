# N6.6 — Numeraciones — Preflight canónico

## Estado y objetivo

- Microtarea: `N6.6.A — Auditoría y preflight`.
- Rama autorizada: `Desarrollo`.
- Base inspeccionada: `851ee4d484b7b03b74720aeac07a9454ae6246da`.
- Dependencias del roadmap: `N6.1.H` y `N6.3.H`, ambas cerradas antes de este preflight.

- Esta microtarea no implementa todavía el modelo ni la migración; delimita el gap, invariantes, riesgos, DoD y estrategia de validación/rollback para B–H.

## Evidencia del estado actual

### Venta

`Venta` persiste `NumeroVenta` como texto. En `VentaService.CreateAsync` el valor inicial es temporal y, después del `INSERT`, se reemplaza por `VEN-{venta.Id:D6}`. El comentario del servicio declara explícitamente que el identificador autoincremental es la única fuente de numeración.

Consecuencia: el correlativo actual es global al `Id` de la tabla; no está particionado por empresa, sucursal ni tipo documental configurable.

### Factura

`Factura` persiste `NumeroFactura` como texto. Durante la confirmación de una venta se crea con un número temporal y luego se reemplaza por `FAC-{factura.Id:D6}`.

Consecuencia: comparte la misma limitación conceptual: secuencia basada en PK global y no en un scope `(Empresa, Sucursal, TipoDocumento)`.

### Autoridad tenant/sucursal disponible

N6.1/N6.3/N6.5 ya establecieron la identidad de empresa, sucursal y aislamiento tenant necesarios para que N6.6 no invente otra fuente de tenant. N6.6 debe consumir esas autoridades existentes y no crear un tenant paralelo.

## Gap material

El sistema no dispone todavía de una autoridad única de numeración documental que garantice simultáneamente:

1. secuencia independiente por `EmpresaId`;
2. secuencia independiente por `SucursalId` cuando el documento pertenece a una sucursal;
3. secuencia independiente por `TipoDocumento`;
4. incremento atómico bajo concurrencia;
5. unicidad del número emitido dentro de su scope;
6. formato/prefijo separado del valor secuencial;
7. continuidad verificable sin depender del PK global de cada tabla;
8. fail-closed cuando falte contexto empresarial/sucursal requerido.

## Alcance propuesto para B–H

### B — Dominio y contratos

Definir una autoridad de secuencia con identidad mínima equivalente a:

`EmpresaId + SucursalId? + TipoDocumento`

El dominio debe distinguir el **valor secuencial** del **formato visible**. No asumir desde A una política fiscal, rango SAR, CAI, punto de emisión u otra regla regulatoria no documentada; esas reglas sólo se incorporan si una fuente funcional posterior las exige explícitamente.

### C — Persistencia y migración

Persistencia durable con constraint único del scope y mecanismo de incremento concurrency-safe. La migración no debe renumerar silenciosamente documentos históricos ni inferir empresa/sucursal cuando el dato sea ambiguo.

### D — Aplicación/API

Servicio único de reserva/emisión de consecutivos. Los documentos consumidores no deben implementar `MAX()+1`, contar filas ni derivar el consecutivo de su PK. La asignación definitiva debe participar en la transacción relevante para evitar duplicados por carreras.

### E — Frontend/UX

Exponer configuración/visualización sólo cuando exista una necesidad de negocio validada. El cliente nunca calcula ni reserva el consecutivo autoritativo.

### F — RBAC/auditoría/seguridad

Auditar cambios de configuración y emisión cuando aplique. Validar tenant/sucursal con las autoridades N6.1/N6.3/N6.5. Ningún header o valor del frontend concede autoridad por sí solo.

### G — QA/CI

Cubrir como mínimo concurrencia, aislamiento entre dos empresas, aislamiento entre dos sucursales de una empresa, dos tipos documentales, rollback/fallo transaccional, unicidad, reintento e historial existente.

### H — Documentación/certificación

Consolidar contratos, migración, rollback, evidencia causal y decisión final de alcance.

## Invariantes obligatorios

1. La misma empresa/sucursal/tipo nunca emite dos veces el mismo consecutivo.
2. Empresas distintas pueden tener el mismo valor secuencial sin colisión lógica.
3. Sucursales distintas pueden tener secuencias independientes cuando el tipo documental se configure por sucursal.
4. Tipos documentales distintos no consumen obligatoriamente la misma secuencia.
5. El siguiente valor no se obtiene con `MAX()+1` ni de un contador en memoria.
6. La concurrencia debe serializar/reservar de forma durable y verificable.
7. Ningún documento histórico se renumera durante la migración sin una regla explícita y reversible.
8. Si el scope requerido está incompleto o no pertenece al tenant actual, la emisión falla cerrado.
9. El PK técnico de Venta/Factura/otros documentos deja de ser la autoridad semántica de numeración para nuevos flujos migrados.
10. Formato visible y contador se modelan separadamente para permitir evolución sin alterar historial.

## Riesgos

- **Colisiones por concurrencia:** dos transacciones leen el mismo último valor.
- **Tenant leakage:** usar una secuencia perteneciente a otra empresa/sucursal.
- **Renumeración accidental:** backfill que cambie referencias históricas o comprobantes emitidos.
- **Huecos:** una reserva consumida y luego revertida; la política sobre huecos debe ser explícita, no inferida.
- **Doble autoridad:** coexistencia indefinida entre PK-based numbering y un nuevo servicio sin frontera de migración clara.
- **Formato acoplado:** usar el string renderizado como estado del contador.
- **Retry no idempotente:** repetir una operación y consumir dos consecutivos.

## Criterios de aceptación para N6.6

- Existe una única autoridad backend para numeración documental.
- El scope empresarial/sucursal/tipo es explícito y validado.
- Persistencia garantiza unicidad/concurrencia.
- Consumidores migrados no dependen de PK/`MAX()+1` para el número semántico.
- Historial permanece preservado.
- Pruebas automatizadas demuestran aislamiento y concurrencia.
- P0=0/P1=0 y gates causales terminales antes de cada cierre aplicable.

## Estrategia de rollback

- A es exclusivamente documental y puede revertirse sin tocar comportamiento.
- B–D deberán mantener cambios de esquema/servicio reversibles y separar adopción de consumidores de la creación de la infraestructura.
- Una migración de datos no podrá borrar/renumerar historia para hacer viable el rollback.
- Ante fallo, se revierte el consumidor nuevo o la configuración mediante commit normal en `Desarrollo`; nunca force-push ni reescritura de historial.
