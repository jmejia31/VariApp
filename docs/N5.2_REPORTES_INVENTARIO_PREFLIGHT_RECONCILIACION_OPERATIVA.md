# N5.2 — Preflight de Reportes de Inventario: Reconciliación Operativa

## Propósito

Levantar evidencia del dominio existente para reportes de reconciliación de inventario —conteos físicos, transferencias, ajustes y movimientos— sin implementar todavía el centro de reportes ni tocar base de datos o Producción.

## 1. Fuentes de datos verificadas

- `ConteoInventario` / `ConteoInventarioDetalle`: preservan stock esperado, cantidad contada, diferencias por línea y agregados como `CantidadConDiferencia` y `DiferenciaNeta`. El servicio además protege la referencia durante conteos ciegos.
- `TransferenciaInventario` / `TransferenciaInventarioDetalle`: preservan almacén/ubicación origen-destino y cantidades solicitadas, aprobadas, despachadas, recibidas, faltantes, sobrantes y dañadas. `RecepcionCerrada` exige reconciliar recibida + faltante + dañada contra lo despachado.
- `AjusteInventario` / `AjusteInventarioDetalle`: el detalle materializa al confirmar `CantidadAnteriorSnapshot`, `CantidadNuevaSnapshot`, `DiferenciaSnapshot`, `CostoUnitarioSnapshot` e `ImpactoCostoSnapshot`. No existe una propiedad canónica llamada simplemente `Diferencia` en el detalle actual.
- `MovimientoInventario`: es la fuente transversal de movimientos de stock y debe evaluarse como origen analítico para trazabilidad y conciliación.

## 2. Contratos operativos reutilizables

Existen APIs y servicios operativos para conteos, transferencias y ajustes. En particular, `ConteosInventarioController` expone búsqueda/detalle y operaciones de ciclo de vida mediante `IConteoInventarioService`; los módulos de transferencias y ajustes cuentan igualmente con entidades, DTOs y servicios especializados. Estas superficies son reutilizables como evidencia de reglas, pero no deben convertirse en múltiples consultas independientes desde el frontend para construir un reporte transversal.

## 3. Contrato analítico faltante

El código actual está orientado a operación por agregado. Para N5.2 falta una superficie analítica explícita que consolide, al menos:

- período y almacén/ubicación;
- producto/variante/SKU;
- origen de la diferencia (`CONTEO`, `TRANSFERENCIA`, `AJUSTE`);
- cantidad esperada/base, cantidad observada/resultante y diferencia normalizada;
- faltante, sobrante o daño cuando aplique;
- costo/impacto económico cuando exista snapshot autorizado;
- documento/origen y marcas de auditoría necesarias para trazabilidad.

También falta un filtro transversal de reporte y un contrato de servicio dedicado —por ejemplo `ReporteInventarioReconciliacionFiltroDto` + servicio de lectura— que evite acoplar la UI a tres servicios operativos distintos.

## 4. Riesgos y reglas para implementación posterior

1. **Semántica:** no mezclar `DiferenciaNeta`, discrepancias de transferencia y `DiferenciaSnapshot` sin una normalización explícita.
2. **Seguridad:** el acceso debe respetar RBAC y alcance por sucursal/almacén; costos e impacto económico requieren tratamiento como datos sensibles.
3. **Rendimiento:** la consulta transversal debe ser de solo lectura, paginada y proyectada; evitar cargar agregados completos o hacer N+1 desde la UI.
4. **Auditoría:** cada fila analítica debe conservar vínculo al documento fuente y evidencia suficiente para explicar la discrepancia.
5. **Conteo ciego:** no filtrar información protegida mientras el ciclo de conteo impida revelar stock esperado/diferencia.

## 5. Dictamen preflight

`N5.2.A.4.RECONCILIATION_OPERATIONS_PREFLIGHT` dispone de dominio operacional suficiente para diseñar el reporte, pero **no existe todavía un contrato analítico transversal dedicado**. La siguiente fase debe implementar dicho contrato reutilizando las invariantes existentes en vez de duplicar lógica de conteos, transferencias o ajustes.
