# N5.2.B.3 — Contrato de dominio de Reconciliación de Inventario

## Propósito

Formaliza la superficie analítica de reconciliación identificada como faltante en N5.2.A, reutilizando las autoridades de conteos, transferencias y ajustes y evitando que Centro de Reportes tenga que normalizar múltiples servicios operativos.

## 1. Contratos materializados

- `ReporteInventarioReconciliacionFiltroDto : ReporteInventarioFiltroBaseDto` añade sólo `ProductoId`, `ProductoVarianteId`, `Sku` y `Origen` al envelope transversal de N5.2.B.1.
- `ReporteInventarioReconciliacionDto` representa una fila analítica con dimensión temporal/física, producto, documento origen, correlación, cantidades normalizadas, discrepancias específicas de transferencia, costo opcional y marcas de auditoría.
- `IReporteInventarioService.ObtenerReporteReconciliacionAsync(...)` mantiene la proyección detrás de un boundary de aplicación de sólo lectura.

`MovimientoInventario` puede participar como evidencia de trazabilidad/correlación, pero no se añade como cuarto `OrigenReconciliacionInventario` para no duplicar la misma discrepancia ya atribuida al documento operativo que la causó.

## 2. Normalización por origen

### Conteo

Sólo una línea cuyo snapshot y diferencia puedan revelarse según el ciclo de conteo puede producir una fila analítica.

- `CantidadEsperada = StockEsperadoSnapshot`.
- `CantidadObservada = CantidadContada`.
- `DiferenciaNormalizada = Diferencia`, una vez cerrada/materializada.
- No se revela stock esperado/diferencia de un conteo ciego mientras el ciclo lo prohíba.

### Ajuste

Sólo se proyectan cantidades de reconciliación cuando existen snapshots de confirmación.

- `CantidadEsperada = CantidadAnteriorSnapshot`.
- `CantidadObservada = CantidadNuevaSnapshot`.
- `DiferenciaNormalizada = DiferenciaSnapshot`.
- `CostoUnitario` / `ImpactoCosto` pueden provenir de `CostoUnitarioSnapshot` / `ImpactoCostoSnapshot`, sujetos al contrato RBAC de N5.2.B.6.

### Transferencia

La reconciliación se basa en la recepción cerrada, sin convertir daños en una diferencia de cantidad inexistente.

- `CantidadEsperada = CantidadDespachada`.
- `CantidadObservada = CantidadRecibida + CantidadDanada + CantidadSobrante`.
- `DiferenciaNormalizada = CantidadSobrante - CantidadFaltante`.
- `CantidadFaltante`, `CantidadSobrante` y `CantidadDanada` se conservan por separado.
- La fila sólo es terminalmente reconciliable cuando `RecepcionCerrada` demuestra `CantidadRecibida + CantidadFaltante + CantidadDanada == CantidadDespachada`.

## 3. Invariantes de trazabilidad y seguridad

- Cada fila conserva `DocumentoId`, `NumeroDocumento` y `CorrelationId` cuando exista evidencia durable.
- Scope físico y permisos se aplican server-side según N5.2.B.6; los filtros del cliente no amplían autoridad.
- Costos/impactos son opcionales y se censuran cuando el permiso financiero no corresponda.
- La proyección no modifica agregados operativos, no ejecuta cierres/aprobaciones y no crea un segundo ledger.

## 4. Frontera con otras facetas

- El envelope común pertenece a N5.2.B.1; esta faceta no duplica período/scope/paginación.
- Valorización/Kardex pertenece a N5.2.B.2 y no se redefine aquí.
- Topología de endpoint/UI pertenece a N5.2.B.4 y fases de implementación posteriores.
- La matriz QA de N5.2.B.5 y el RBAC de N5.2.B.6 gobiernan aceptación/censura sin incorporarse a este DTO como lógica.

## 5. Acceptance para N5.2.C+

La implementación deberá probar causalmente los tres mappings anteriores, conteo ciego, recepción cerrada, snapshots de ajuste, trazabilidad al origen, paginación y aislamiento RBAC. Ninguna prueba puede sustituirse por una etiqueta `PASS` si no corresponde al HEAD que se certifica.
