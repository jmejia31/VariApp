# N5.1 — Centro de Reportes: QA / rollback preflight

## Propósito

Este documento define el preflight de aceptación para el `CURRENT_PARENT=N5.1.A`. Distingue estrictamente entre **contrato observable hoy en `Desarrollo`** y **checks propuestos para la implementación futura**. No declara resultados de tests que no hayan sido ejecutados ni comportamiento que el código actual no demuestre.

## 1. Contrato observable actual

Fuente primaria: `backend/src/API/Controllers/ReportesAdministrativosController.cs`.

El controlador actual está protegido por `[Authorize]`, usa la ruta base `reportes-administrativos` y exige permisos del módulo `ReportesAdministrativos`. Además, cada acción verifica `_currentUser.EsAdministrador` y devuelve `Forbid()` cuando no se cumple.

| Operación observable | Ruta actual | Permiso declarado | Nota |
| --- | --- | --- | --- |
| Resumen | `GET /reportes-administrativos/resumen` | `Ver` | Recibe `ReporteAdministrativoFiltroDto`. |
| Usuarios/accesos | `GET /reportes-administrativos/usuarios-accesos` | `Ver` | Solo administrador además del permiso. |
| Roles/permisos | `GET /reportes-administrativos/roles-permisos` | `Ver` | Solo administrador además del permiso. |
| Resumen de auditoría | `GET /reportes-administrativos/auditoria-resumen` | `Ver` | Recibe `ReporteAdministrativoFiltroDto`. |
| Exportación | `GET /reportes-administrativos/exportar/{tipo}?formato=...` | `Exportar` | Registra auditoría explícita de la exportación y retorna archivo. |

No forman parte del contrato observable de este controlador rutas como `/inventario`, `/ventas`, `/compras` ni `/exportar` sin `{tipo}`. Si N5.1 necesita endpoints independientes para esos dominios, deben implementarse y probarse explícitamente en una fase posterior.

## 2. Matriz de aceptación ejecutable

Los siguientes checks son el contrato de QA para N5.1. Un escenario marcado **GAP** no debe contarse como PASS hasta que exista implementación y evidencia causal.

### A. Autenticación y autorización

| ID | Escenario | Acción | Resultado esperado | Estado preflight |
| --- | --- | --- | --- | --- |
| A1 | Sin token | Invocar cualquier ruta protegida | 401 | TEST REQUERIDO |
| A2 | Autenticado sin permiso `Ver` | `GET /reportes-administrativos/resumen` | 403 | TEST REQUERIDO |
| A3 | Permiso `Ver`, pero usuario no administrador | `GET /reportes-administrativos/resumen` | 403 por guard de administrador | TEST REQUERIDO |
| A4 | Administrador con permiso `Ver` | Invocar las cuatro rutas de lectura | Respuesta de aplicación válida sin bypass RBAC | TEST REQUERIDO |
| A5 | Tiene `Ver` pero no `Exportar` | `GET /reportes-administrativos/exportar/{tipo}` | 403 | TEST REQUERIDO |
| A6 | Administrador con `Exportar` | Exportar un tipo/formato soportado | Archivo retornado y auditoría de exportación persistida | TEST REQUERIDO |

### B. Filtros y límites de consulta

`ReporteAdministrativoFiltroDto` es el contrato actual para las operaciones que reciben filtros. Antes de certificar N5.1 deben existir pruebas que cubran al menos:

| ID | Escenario | Resultado esperado | Estado preflight |
| --- | --- | --- | --- |
| B1 | Rango de fechas válido | Respuesta coherente con el rango | TEST REQUERIDO |
| B2 | `Desde > Hasta` | Rechazo fail-closed o validación explícita definida por contrato | GAP: verificar/implementar regla |
| B3 | Rango extremo o no acotado | No debe habilitar consulta materialmente ilimitada sin política explícita | GAP: política de límites requerida |
| B4 | Parámetros opcionales omitidos | Comportamiento determinista documentado | TEST REQUERIDO |

No se presume que existan filtros `sucursalId`, usuario u otros campos no demostrados por el DTO vivo.

### C. Estados de interfaz

Para la UI del centro de reportes, los E2E deben cubrir como mínimo:

| ID | Escenario | Resultado esperado | Estado preflight |
| --- | --- | --- | --- |
| C1 | Request en curso | Estado de carga visible; no aplicar respuestas stale | TEST/E2E REQUERIDO |
| C2 | Resultado vacío | Estado vacío estable, sin error de render | TEST/E2E REQUERIDO |
| C3 | Error HTTP/transport | Error visible y estado de carga liberado | TEST/E2E REQUERIDO |
| C4 | Cambio de filtros con request anterior pendiente | La respuesta vieja no sobrescribe el filtro vigente | EVIDENCIA EXISTENTE EN `/reportes-administrativos`; mantener como regresión |

### D. Integridad histórica

Estos escenarios son requisitos de aceptación futura, no afirmaciones sobre capacidades ya implementadas:

| ID | Riesgo | Evidencia exigida antes de PASS |
| --- | --- | --- |
| D1 | Reportes históricos cambian al editar catálogos actuales | Fixture histórico + aserción sobre datos persistidos de la transacción original. |
| D2 | Soft-delete rompe referencias históricas | Fixture con entidad inactiva/eliminada lógicamente + reporte histórico consistente. |
| D3 | Costo/utilidad se recalcula con valores actuales | Prueba contra la política de costeo realmente implementada; si N5.1 no ofrece este reporte, marcar N/A de forma explícita. |

### E. No regresión, rendimiento y rollback

| ID | Check | Criterio |
| --- | --- | --- |
| E1 | No regresión | Los tests existentes de backend/frontend relacionados con reportes deben continuar verdes en el exact HEAD integrado. |
| E2 | Rollback | Cambios propios de N5.1 deben poder revertirse sin modificar contratos transaccionales de Ventas, Compras o Inventario que no pertenezcan al scope. |
| E3 | Solo lectura | Las consultas de reportes no deben mutar dominio transaccional; cualquier escritura debe limitarse a efectos explícitos permitidos, como la auditoría de exportación ya observable. |
| E4 | Rendimiento | Definir presupuesto medible antes de certificar; no se fija arbitrariamente un umbral de milisegundos sin benchmark/SLI aprobado. |
| E5 | Exportaciones grandes | Definir límite/paginación/streaming o estrategia asíncrona con prueba; no se inventa un máximo de filas mientras no exista contrato aprobado. |

## 3. Evidencia mínima para cerrar N5.1.A.4

Para REVIEW_PASS se exige:

1. Esta matriz contrastada contra el controlador/DTO/UI vivos del exact HEAD.
2. Cualquier escenario marcado GAP debe permanecer como GAP hasta que exista implementación o decisión explícita de alcance.
3. No declarar 401/403/200, auditoría, performance o integridad como PASS sin test o evidencia causal correspondiente.
4. Preservar la regresión existente contra stale responses de `/reportes-administrativos`.
5. Validar que el cambio de este preflight sea documentación-only y no toque código de producto, manifests, secretos, Producción ni `main`.

## 4. Rollback boundary

Este preflight es documentación-only. Su rollback es la reversión de este archivo. No requiere migración de base de datos ni cambio de configuración. La futura implementación de N5.1 debe mantener un rollback separado por cambios de frontend, backend y persistencia, evitando acoplar la reversión del centro de reportes a módulos transaccionales no pertenecientes al scope.
