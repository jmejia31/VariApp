# N5.9.B — Rendimiento de reportes — decisión de dominio y contratos

Autoridad operativa: `docs/VAEP_AUTHORITY.md`.

## Decisión: N/A para nuevo dominio

No se requiere crear una entidad, agregado, value object, evento de dominio ni interfaz de negocio nueva únicamente para mejorar el rendimiento de reportes. El problema identificado por `N5.9.A` está en la forma de ejecutar lecturas (queries, índices, round-trips y proyecciones), no en una ausencia de invariantes de negocio.

Los contratos actuales ya expresan los casos de uso que deben preservarse:

- `IReporteVentasService` expone resumen y detalle paginado con `ReporteVentasFiltroDto`.
- `IReporteInventarioService` y sus DTOs/filtros ya separan las lecturas especializadas de inventario.
- `IReporteComprasService` expone detalle paginado de compras.
- Los servicios de infraestructura materializan esas lecturas con `AsNoTracking`, filtros server-side y DTOs especializados.

## Invariantes que N5.9 debe conservar

1. Paginación y límites de los reportes permanecen contractuales; una optimización no puede convertirlos en cargas sin límite.
2. Filtros, orden y semántica temporal mantienen sus contratos actuales.
3. RBAC y row scope siguen fail-closed; una cache/read model no puede ampliar datos visibles.
4. Cálculos financieros/de inventario/compras no cambian de significado por una optimización de acceso.
5. Cualquier cache futura es una optimización de aplicación/infrastructura y no una nueva fuente de verdad de dominio.
6. Vistas, índices, read models físicos o agregados persistidos sólo se justifican en N5.9.C/D con evidencia causal y rollback.

## Implicación para N5.9.C y N5.9.D

`N5.9.C` debe concentrarse en mappings/índices/migraciones estrictamente ligados a predicates, joins u ordering observados. `N5.9.D` debe concentrarse en queries/read models especializados y reducción segura del patrón causal, preservando las interfaces públicas salvo que una medición pruebe que un contrato actual impide una solución correcta.

Crear un `ReportPerformance` domain model, una facade genérica o DTOs nominales sin necesidad funcional sería filler y está prohibido por el MAESTRO.

## Validación dirigida

La decisión fue contrastada con `docs/N5.9_REPORT_PERFORMANCE_PREFLIGHT.md`, `backend/src/Application/Interfaces/IReporteVentasService.cs` y los servicios de ventas/inventario/compras inspeccionados en A. No se encontró un gap de dominio necesario para el objetivo de rendimiento.

## Rollback

Este parent sólo documenta una decisión de aplicabilidad y no cambia runtime, persistencia, API ni UI. Su rollback es revertir este documento/receipt si una evidencia posterior demuestra un contrato de dominio realmente necesario.
