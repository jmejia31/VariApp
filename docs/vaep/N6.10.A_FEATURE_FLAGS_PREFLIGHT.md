# N6.10.A — Feature flags por empresa/plan — PRE

## Alcance y autoridad

Parent canónico: `N6.10.A`  
Etapa: `PRE`  
Branch permitido: `Desarrollo`  
Salida requerida por COLA: auditoría de feature flags y preflight de módulos por plan, sin implementar cambios grandes.

Este documento separa explícitamente el estado actual comprobado del contrato propuesto para la siguiente etapa. No declara que exista hoy un sistema de feature flags si el código no lo demuestra.

## Estado actual comprobado

1. `PlanSaaS` modela plan, código, estado y una colección genérica de `PlanLimite` (`Clave`/`Valor`).
2. `SuscripcionSaaS` vincula `EmpresaId` con `PlanId` y estado/vigencia de la suscripción.
3. `SuscripcionesSaaSService.ObtenerLimitesAsync(EmpresaId)` obtiene la suscripción activa y devuelve los límites del plan como diccionario por clave.
4. `SuscripcionesSaaSController` expone la consulta de límites de la suscripción efectiva.
5. La inspección dirigida del árbol de `Desarrollo` no encontró un tipo, archivo o endpoint dedicado denominado `FeatureFlag`/`FeatureFlags`.
6. No se encontró en la fuente inspeccionada una tabla autoritativa que asigne módulos concretos a los códigos de plan `FREE` y `PRO`.

Consecuencia: los límites genéricos existentes no deben reinterpretarse silenciosamente como feature flags de módulos. Hacerlo mezclaría dos contratos distintos y podría habilitar funcionalidad sin política explícita.

## Riesgos P0/P1 que debe evitar N6.10

- **P0 — aislamiento tenant:** nunca aceptar `EmpresaId`, plan ni feature habilitada desde el cliente como autoridad. La evaluación debe partir del tenant verificado por servidor.
- **P0 — fail open:** un plan desconocido, suscripción inexistente/no vigente, módulo desconocido o política ausente debe resultar en feature deshabilitada.
- **P1 — UI como enforcement:** ocultar/mostrar un módulo en frontend no sustituye autorización backend.
- **P1 — semántica ambigua:** no reutilizar una `PlanLimite.Clave` como bandera booleana sin contrato explícito y versionado.
- **P1 — contaminación cross-tenant:** cache, lookup o evaluación de entitlement debe incluir `EmpresaId` y no compartir decisiones entre empresas.
- **P1 — divergencia plan/política:** la política debe resolver sobre el plan efectivo de la suscripción activa y un identificador canónico estable del módulo.

## Contrato propuesto para la siguiente etapa

La siguiente etapa debe introducir una política explícita de entitlement de módulos, separada de los límites cuantitativos.

Entrada mínima autoritativa:

- `EmpresaId` obtenido del contexto tenant validado por servidor.
- Suscripción activa/vigente de esa empresa.
- `PlanSaaS` activo correspondiente a la suscripción.
- `module_key` canónico, estable y definido por servidor.

Resultado mínimo:

- `enabled = true` sólo cuando existe una regla explícita para el plan efectivo y el `module_key` solicitado.
- En cualquier otro caso: `enabled = false`.
- La respuesta puede incluir motivo/código de decisión para auditoría, pero no debe revelar datos de otro tenant.

## Checklist por plan

La COLA exige preflight para Free/Pro. El estado actual no contiene una matriz autoritativa de módulos concretos, por lo que este PRE define condiciones de aceptación sin inventar habilitaciones.

### FREE

- [ ] El código canónico `FREE` debe tener una allowlist explícita de `module_key` en la implementación siguiente.
- [ ] Un módulo no presente en la allowlist de FREE queda deshabilitado.
- [ ] La política no debe inferir enablement a partir de precio, nombre visible del plan o datos enviados por cliente.
- [ ] Los límites cuantitativos de FREE permanecen separados del enablement de módulos.

### PRO

- [ ] El código canónico `PRO` debe tener una allowlist explícita de `module_key` en la implementación siguiente.
- [ ] No se asume que PRO habilita todos los módulos; sólo habilita reglas explícitas.
- [ ] Un módulo no presente en la allowlist de PRO queda deshabilitado.
- [ ] Los límites cuantitativos de PRO permanecen separados del enablement de módulos.

### Casos sin plan utilizable

- [ ] Sin suscripción activa: todos los módulos evaluados quedan deshabilitados.
- [ ] Suscripción expirada/cancelada/no vigente: fail closed.
- [ ] Plan inexistente o inactivo: fail closed.
- [ ] Código de plan desconocido: fail closed.
- [ ] `module_key` desconocido o vacío: fail closed.

## Condiciones de habilitación

Una feature de módulo sólo puede quedar habilitada cuando todas estas condiciones son verdaderas:

1. Existe contexto tenant server-side verificado.
2. La empresa consultada coincide exactamente con el `EmpresaId` del contexto.
3. Existe una suscripción activa y vigente para esa empresa.
4. El plan asociado existe y está activo.
5. El plan tiene un código canónico reconocido por la política.
6. El `module_key` solicitado es canónico y conocido.
7. Existe una regla explícita plan -> módulo que habilita ese `module_key`.

La ausencia de cualquiera de las condiciones anteriores debe producir `disabled` sin fallback permisivo.

## Smokes dirigidos requeridos

1. **FREE / módulo permitido:** empresa con plan FREE y regla explícita para `module_key=A` => enabled.
2. **FREE / módulo no permitido:** misma empresa, `module_key=B` sin regla => disabled.
3. **PRO / módulo permitido:** empresa con plan PRO y regla explícita para `module_key=A` => enabled.
4. **PRO / módulo no declarado:** módulo sin regla explícita => disabled; no existe wildcard implícito.
5. **Tenant cruzado:** contexto de Empresa A intentando evaluar Empresa B => rechazado/fail closed.
6. **Sin suscripción:** empresa válida sin suscripción activa => disabled.
7. **Suscripción no vigente:** expirada/cancelada => disabled.
8. **Plan inactivo/desconocido:** disabled.
9. **Módulo desconocido:** disabled.
10. **Spoof de cliente:** `EmpresaId`, plan o enablement enviado por cliente no altera la decisión autoritativa.
11. **Separación límites/features:** modificar un límite cuantitativo no habilita por sí mismo ningún módulo.
12. **Aislamiento de cache:** una decisión de Empresa A no puede reutilizarse para Empresa B.

## REVIEW_FIRST — criterios de aceptación de N6.10.A

N6.10.A puede considerarse apto para cierre PRE sólo si:

- Estado actual y contrato futuro están separados explícitamente.
- No se afirma una implementación de feature flags inexistente.
- Existe checklist Free/Pro sin inventar asignaciones de módulos.
- Están definidas condiciones server-side de habilitación y fail-closed.
- Están definidos smokes dirigidos que cubren tenant, vigencia, plan, módulo y spoofing.
- Queda explícita la separación entre límites cuantitativos y feature/module entitlements.
- No se introduce implementación funcional grande en PRE.
- REVIEW_FIRST termina con P0=0 y P1=0 para este alcance documental/preflight.
