## 2. Recovery invariants

Every rollback or forward-recovery attempt must preserve all of the following:

1. DEV only; `main` and Production remain untouched.
2. The exact current and previous-known-good revisions must be recorded before provider action.
3. Health/readiness must be captured before the attempt, after the previous-known-good target becomes active, and after return to the current target.
4. A provider operation already in progress, an unknown target, or ambiguous environment identity is a STOP condition.
5. Active DEV database data must never be overwritten by a destructive `Down` migration.
6. Database recovery uses a verified isolated restore or an explicit forward-fix. `BACKUP_REAL=PASS` and `RESTORE_ISOLATED=PASS` remain causal prerequisites.
7. Secret values, connection strings, tokens, customer payloads and Production business data never enter receipts or runbooks.
8. `P0=0` and `P1=0` are mandatory before a rollback result can be certified.
9. Failed attempts remain evidence; they are not rewritten into PASS.

## 3. Deterministic decision tree

### A. Is the incident code/configuration-only with data integrity intact?

- **Yes:** evaluate application rollback to the exact previous-known-good backend/frontend target.
- **No or unknown:** STOP application rollback until database/schema compatibility is proven. Continue with section B.

### B. Is there suspected schema drift, destructive migration impact, or data corruption?

- **Yes:** do **not** run destructive `Down` against active DEV. Select one of:
  - verified isolated restore from the validated backup path, then validate before any cutover; or
  - forward-fix migration/code change when it preserves data and is demonstrably safer.
- **No:** application rollback may proceed only after current/previous schema compatibility is proven.

### C. Does the previous-known-good application revision require a database schema older than the active schema?

- **Yes or unknown:** STOP provider rollback. Prefer forward-fix or an isolated recovery candidate; do not guess compatibility.
- **No:** application rollback may proceed once health baseline and ownership are valid.

### D. After rollback, is readiness/health green and are directed smoke checks passing?

- **Yes:** record elapsed time and evidence, then execute the required return path `PREVIOUS_KNOWN_GOOD -> CURRENT` when authorized for the execution stage.
- **No:** STOP. Do not continue to the return path as if the rollback passed. Preserve evidence, classify the failure, and either restore the last proven target or choose forward-fix.

### E. After returning to CURRENT, is health green again?

- **Yes:** the application rollback cycle may be considered technically successful only after the causal test/security gates also pass.
- **No:** the cycle fails. Preserve the previous-known-good candidate and invoke recovery ownership; no `LISTO` is allowed.

## 4. STOP conditions

Any one of these conditions halts the active rollback attempt:

- environment is not unambiguously DEV/`Desarrollo`;
- current or previous-known-good target is missing/unknown;
- another provider deployment/rollback is active for the same service/project;
- current health baseline is already red and the failure mode is not understood;
- database backup/restore prerequisite is not proven;
- previous application revision is not proven compatible with the active schema;
- rollback would require destructive `Down` on active DEV;
- required credentials/access are unavailable to the authorized operator;
- a new P0 or P1 appears;
- tenant isolation, authz, database integrity, or audit evidence cannot be verified;
- any step would touch `main`, Production, secrets, PR #2, or an out-of-scope provider resource.

A STOP is not a failed certification by itself; it is a safety outcome that must be persisted and resolved before resuming.

## 5. Forward-fix semantics

Forward-fix is preferred over application rollback when rolling backward would create schema incompatibility, lose data, require destructive `Down`, or revive a known security/integrity defect.

A forward-fix must:

1. be scoped to the smallest causal defect;
2. preserve current data and migration history;
3. pass directed tests and database integrity checks;
4. pass REVIEW_FIRST with P0=0/P1=0;
5. leave an immutable receipt identifying the exact candidate head;
6. never be used as a label to conceal an unexecuted rollback requirement.

## 6. Ownership and responsibilities

- **Incident/Recovery Coordinator:** owns the decision tree, timestamps, STOP/resume decisions, and confirms the scope remains DEV-only.
- **Application Platform Operator:** owns exact Render/Vercel target identity, provider-native rollback/return actions when explicitly authorized, and health/readiness capture.
- **Database Recovery Operator:** owns schema compatibility, restore/forward-fix choice, isolated recovery target validation, and the prohibition on destructive active-DB `Down`.
- **Security Reviewer:** owns authn/authz, tenant isolation, secret/PII hygiene, auditability, and P0/P1 classification.
- **Evidence/VAEP Closer:** owns REVIEW_FIRST, causal gate mapping, candidate-head equivalence, receipt creation, Sheet transition, readback, and dependency promotion.

A person/automation may hold more than one role, but there must be one explicit writer lease for each material VAEP scope.

## 7. Evidence required for an executable rollback cycle

For each backend/frontend leg capture:

- UTC start and end timestamps;
- provider service/project and deployment ids;
- immutable Git SHAs for CURRENT and PREVIOUS_KNOWN_GOOD;
- pre-action health/readiness;
- provider terminal state for the previous target;
- post-rollback health/readiness and directed smoke result;
- elapsed rollback time;
- return-to-current action and terminal state;
- post-return health/readiness and directed smoke result;
- elapsed return time;
- database compatibility/integrity result;
- REVIEW_FIRST and final P0/P1 counts;
- exact-head/equivalence statement;
- receipt and Sheet readback.

The required N8.23 sequence is `CURRENT -> PREVIOUS_KNOWN_GOOD -> HEALTHY -> CURRENT -> HEALTHY`. Merely naming rollback candidates does not satisfy that execution gate.
