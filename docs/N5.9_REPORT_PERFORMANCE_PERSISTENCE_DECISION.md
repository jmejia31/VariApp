# N5.9.C — Rendimiento de reportes — decisión de persistencia e índices

Autoridad operativa: `docs/VAEP_AUTHORITY.md`.

## Alcance inspeccionado

Esta microtarea revisa exclusivamente si el hotspot Stock Health de `ReporteInventarioService` justifica una migración/índice nuevo antes de la optimización de aplicación de N5.9.D. No ejecuta Producción ni modifica datos.

## Query shape observado

Stock Health correlaciona `MovimientoInventario` por `ProductoVarianteId`, `AlmacenId` y `UbicacionAlmacenId`; calcula `Max(Fecha)` y, para salidas del período, filtra además `Tipo == Salida` y un rango de `Fecha` antes de sumar `Cantidad`.

La configuración EF vigente ya contiene un índice por `ProductoVarianteId`, `(ProductoId, ProductoVarianteId, Fecha)`, `(AlmacenId, UbicacionAlmacenId)` y `(AlmacenId, UbicacionAlmacenId, Fecha)`, además de índices temporales para varias FKs. Ninguno combina exactamente las tres claves físicas del subquery de Stock Health con `Fecha`.

## Decisión

**No se autoriza una migración/índice nuevo en N5.9.C.** Esto es una decisión N/A deliberada, no un bloqueo.

Motivos causales:

1. El plan de persistencia ya aceptado en N5.2 estableció que un índice adicional para reportes requiere evidencia de plan/perfil (`EXPLAIN` o equivalente en entorno descartable), para evitar índices nominales y coste de escritura no justificado.
2. El hotspot actual contiene subconsultas correlacionadas por existencia. N5.9.D está específicamente reservado para eliminar o reducir primero ese patrón mediante una query/read-model especializada manteniendo paginación y row scope.
3. Añadir ahora un índice compuesto antes de fijar el query shape posterior a N5.9.D podría optimizar una forma de consulta que dejará de existir y sería trabajo especulativo.
4. Los índices existentes proporcionan cobertura parcial suficiente para conservar corrección; no existe evidencia reproducible en este scope que demuestre que una nueva estructura física sea necesaria antes del cambio de aplicación.

Por tanto, N5.9.C se resuelve como **PERSISTENCE_INDEX_CHANGE_NOT_APPLICABLE_YET**: sin migración, sin snapshot delta y sin backfill. La necesidad de índice se reevalúa sólo si el query shape final de N5.9.D y evidencia de plan descartable demuestran un gap residual.

## Seguridad y rollback

- Producción: no tocada.
- Datos: no mutados.
- `main`: no tocada.
- Secrets/deploy: no tocados.
- Rollback de esta decisión documental: revertir el documento; no existe migración que deshacer.

## Handoff causal a N5.9.D

N5.9.D debe optimizar el hotspot de Stock Health preservando exactamente:
- `IUsuarioScopeService` y fail-closed por usuario;
- filtros físicos de variante/almacén/ubicación;
- semántica de `UltimoMovimientoUtc` y `UnidadesSalidaPeriodo`;
- paginación y orden determinista;
- resultados de los tipos StockBajo/Agotado/SinMovimiento/Aging/Rotacion.

Después del cambio de aplicación, sólo una evidencia de plan estable puede justificar volver a persistencia para agregar un índice. No se debe crear una estructura física para cumplir una cuota de trabajo.
