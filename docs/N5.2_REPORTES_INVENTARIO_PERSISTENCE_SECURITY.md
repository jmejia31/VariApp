# N5.2.C.6 — Requisitos de seguridad en persistencia para Reportes de Inventario

## Propósito

Traducir a requisitos de consulta/persistencia los contratos de RBAC, scope, censura económica, auditoría y bounded queries fijados en N5.2.B.6, sin afirmar que esos controles futuros ya están implementados.

## 1. Autorización y scope físico

La autorización de backend precede a la consulta analítica:

- Reconciliación: `ModuloSistema.Inventario + AccionPermiso.Ver`; exportación `Inventario + Exportar`.
- Movimientos/Kardex: `ModuloSistema.MovimientosInventario + AccionPermiso.ConsultarHistorial`; exportación `MovimientosInventario + Exportar`.
- Stock analytics/valorización: permiso base `ModuloSistema.Inventario + AccionPermiso.Ver`.

Los filtros de sucursal/almacén deben intersectarse server-side con la autoridad real del usuario **antes** de paginar/materializar datos. Sin filtro explícito, la consulta se restringe al conjunto autorizado. Si el cliente pide explícitamente un scope fuera de su autoridad, el contrato exige **403 fail-closed**; no se acepta degradar silenciosamente a una consulta vacía o distinta.

## 2. Censura de costos/valorización

Los campos económicos requieren, además del permiso base del reporte, `ModuloSistema.Finanzas + AccionPermiso.Ver`.

- Sin permiso financiero, `CostoUnitario`, valorizaciones e impactos económicos deben proyectarse como `null`/omisión contractual, nunca como `0` ficticio.
- La implementación debe preferir que la proyección autorizada evite transportar datos económicos innecesarios a memoria de aplicación.
- Esta censura no modifica el scope físico autorizado.

## 3. Auditoría

Las **exportaciones** de reportes de inventario reutilizan `IAuditoriaService` y deben registrar al menos actor, módulo/acción, tipo de reporte, resultado y filtros materiales. No se crea una segunda autoridad de auditoría.

Las consultas JSON ordinarias no se convierten automáticamente en eventos de auditoría sólo por ser analíticas; cualquier auditoría adicional deberá justificarse por el contrato de la fase funcional, sin inventar requisitos no fijados en N5.2.B.6.

## 4. Bounded queries

Guardrails obligatorios para los endpoints analíticos nuevos:

- ventana histórica máxima de 366 días para movimientos/reconciliación;
- paginación obligatoria para JSON;
- exportación limitada a 50,000 filas por solicitud;
- petición fuera de límites => error de validación antes de ejecutar una consulta sin cota.

La implementación de persistencia debe aplicar filtros de autorización y ventana antes de `Skip/Take`/materialización y conservar orden determinista. No se prescribe una sintaxis SQL específica (`OFFSET/FETCH` vs `LIMIT`) porque la traducción depende del proveedor MySQL/EF y debe probarse en la implementación real.

## 5. Matriz causal para N5.2.D+

1. Falta permiso base => denegación.
2. Scope explícito no autorizado => `403`, sin fuga horizontal.
3. Sin `Finanzas/Ver` => cantidades visibles según permiso base y campos económicos censurados como `null`/omisión.
4. Exportación => evento de auditoría verificable con actor, acción, tipo, resultado y filtros materiales.
5. Ventana >366 días, JSON sin paginación válida o exportación >50,000 filas => rechazo de validación sin consulta ilimitada.
6. Filtros/scope se aplican en servidor antes de materialización; cliente/UI no amplían autoridad.
