## Arquitectura real dirigida

### Reporte de ventas

`backend/src/Infrastructure/Services/ReporteVentasService.cs` ya evita materializar el agregado transaccional completo: usa `AsNoTracking()`, filtros server-side, proyecciones y paginación. El resumen agrega en SQL. El detalle ejecuta un `CountAsync` y después la página, y usa subqueries/`Contains` para filtros por dimensiones. Esto es una base de read-query válida; N5.9 no debe reemplazarla por un segundo dominio o una cache sin evidencia.

### Reporte de inventario

`backend/src/Infrastructure/Services/ReporteInventarioService.cs` usa `AsNoTracking()` y filtros server-side. El Stock Health proyecta por existencia y calcula `UltimoMovimientoUtc` y `UnidadesSalidaPeriodo` mediante subconsultas correlacionadas contra movimientos. Además ejecuta `CountAsync` y después la página. Este camino es candidato principal para optimización medida porque el costo puede crecer con existencias y movimientos aunque la salida esté paginada.

La reconciliación combina fuentes heterogéneas y toma resultados parciales antes de consolidar; cualquier optimización debe preservar orden, paginación y scope de usuario, no convertir el reporte en una lectura sin límites.

### Reporte de compras

`backend/src/Infrastructure/Services/ReporteComprasService.cs` usa `AsNoTracking()`, pagina primero el conjunto base y después resuelve facturas, recepciones, devoluciones y evaluaciones con consultas acotadas a los IDs de la página. La estrategia evita cargar todo el grafo, pero produce varios round-trips por request (count + página base + lecturas complementarias). Es candidato para reducción de round-trips/read-model especializado sólo si las pruebas demuestran equivalencia de semántica.

## Riesgos y deuda causal

1. **Consultas correlacionadas de Stock Health.** `Max` y `Sum` por existencia pueden amplificar trabajo SQL. Prioridad: medir/inspeccionar SQL y resolver con query especializada/agrupación previa o índice apropiado, sin cambiar resultados.
2. **Round-trips del reporte de compras.** El fan-out está limitado por la página y es correcto funcionalmente, pero puede dominar latencia. Prioridad: mantener page-first y consolidar sólo donde una query especializada siga siendo legible y testeable.
3. **Filtros dimensionales de ventas.** Los subqueries `Contains` son server-side y correctos; antes de añadir índices/vistas debe verificarse el patrón exacto de filtros y columnas ya indexadas.
4. **Índices sin medición.** No se autoriza crear índices nominales para “optimizar”. N5.9.C debe inspeccionar mappings/migraciones y añadir sólo índices ligados a predicates/order/join observados, con migración reversible.
5. **Caching.** No es default. Sólo se permite si existe lectura repetida, key completa (incluyendo scope/usuario/filtros), TTL/invalidation explícitos y pruebas que impidan fuga cross-scope o datos obsoletos peligrosos.
6. **RBAC/row scope.** Toda optimización debe conservar el fail-closed actual; rendimiento nunca justifica omitir `IUsuarioScopeService`, permisos, filtros de tenant/usuario ni auditoría aplicable.

## Decisiones para N5.9.B–H

- **N5.9.B / dominio y contratos:** no se justifica una nueva entidad de dominio por rendimiento. Si la inspección de contratos confirma que DTOs/filtros existentes expresan la consulta, B debe documentarse N/A y evitar un dominio artificial.
- **N5.9.C / persistencia:** inspeccionar índices y SQL generado de los hotspots. Materializar sólo migraciones/índices que correspondan a predicates, joins y ordering reales; rollback obligatorio. No ejecutar Producción.
- **N5.9.D / aplicación/API:** optimizar primero el hotspot con mayor causalidad verificable, manteniendo paginación, DTOs, HTTP y autorización. Preferir una query/read model especializada antes que una capa de cache genérica.
- **N5.9.E / frontend:** N/A salvo que backend introduzca un contrato visible necesario para paginación/estado. No añadir UI “de rendimiento”.
- **N5.9.F / seguridad/observabilidad:** verificar que cualquier cache/read model preserve scope y añadir medición/telemetría sólo si el seam ya existe y es proporcional.
- **N5.9.G / QA/CI:** incluir regresión funcional y una prueba dirigida que impida reintroducir el patrón causal optimizado; no usar umbrales temporales frágiles como único gate.
- **N5.9.H / certificación:** documentar exactamente qué cambió, evidencia exact-head, rollback y límites; no afirmar mejora cuantitativa sin benchmark reproducible.

## Criterios de aceptación derivados

- Las consultas continúan read-only y bounded/paginadas donde hoy lo son.
- No se modifica semántica financiera, inventario, compras, ventas, RBAC ni row scope para ganar velocidad.
- Cada optimización futura tiene un hotspot causal identificado y test de regresión.
- Migraciones/índices, si existen, son reversibles y no se ejecutan en Producción desde VAEP.
- Caching, vistas o agregados sólo se introducen con necesidad demostrable, no por preferencia arquitectónica.
- No se declara una mejora porcentual sin benchmark reproducible; el DoD se prueba por equivalencia funcional + eliminación del patrón causal seleccionado + gates exact-head.
